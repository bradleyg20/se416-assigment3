## Part 2
### a.
What was wrong:
1. High cyclomatic complexity – seven chained instanceof tests make the loop hard to read and maintain.

2. Tight coupling to concrete classes – every time a new POIXMLDocumentPart is added, the chain must be edited (violates the open/closed principle).

3. Low cohesion – the loop does three different things: (i) decides the part type, (ii) mutates workbook fields, (iii) occasionally inserts items into side-maps.

4. Hidden intent – a reader must scan the whole chain to learn which part types the workbook supports.

### b.
They are only minimally adequate
| Step in `setSheetName`                                                | Current behaviour                                                                                                                                            | Why it is **not fully sufficient**                                                                                                                                     | Concrete improvement                                                                                                                                     |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1  Null check**<br>`if (sheetname == null)`                         | Throws `IllegalArgumentException` (“sheetName must not be null”).                                                                                            | Acceptable, but three different error cases in this method already use the *same* exception class, making it impossible for callers to react differently.              | Introduce a dedicated unchecked type such as `NullSheetNameException` **or** at least prefix message with a code (“ERR-NULL”).                           |
| **2  Index check**<br>`validateSheetIndex(sheetIndex)`                | `validateSheetIndex` throws `IllegalArgumentException` when the index is out of range.                                                                       | Java convention for a bad numeric index is `IndexOutOfBoundsException`; re-using `IAE` hides intent.                                                                   | Change `validateSheetIndex` to throw `IndexOutOfBoundsException` (or a POI-specific `InvalidSheetIndexException`).                                       |
| **3  Name length > 31**<br>silently truncated                         | The name is shortened in-place; no exception is raised.                                                                                                      | Violates “fail-fast” and **least-astonishment** guidelines—data loss without warning. Truncation also breaks round-trip equality (caller cannot know the stored name). | Either **throw** (`SheetNameTooLongException`) or provide an overload/flag that lets the caller opt-in to Excel-style truncation, and document clearly.  |
| **4  `WorkbookUtil.validateSheetName`**                               | May throw `IllegalArgumentException` for invalid chars. Exception text comes from deep utility, no workbook context.                                         | Caller gets an opaque message like “Invalid character (0x003A) in sheet name”, without sheet index/location.                                                           | Catch that `IAE`, wrap as `POIXMLException` or re-throw with enriched context:  `"Invalid sheet name '" + sheetname + "' in workbook": + e.getMessage()` |
| **5  Duplicate-name check**<br>`containsSheet(sheetname, sheetIndex)` | Another `IllegalArgumentException` (“workbook already contains…”)                                                                                            | Same type again; library user must parse message strings to know which rule failed.                                                                                    | Distinct runtime type (`DuplicateSheetNameException`).                                                                                                   |
| **6  Formula update**<br>`utils.updateSheetName(…)`                   | If formula parsing fails, an unchecked `FormulaParseException` (or similar) escapes **after** the name has been truncated but **before** the XML is renamed. | Potential for *inconsistent state*: caller sees an exception but can’t know whether any internal rename occurred.                                                      | Wrap in `try/catch`; only call `setName` if update succeeds, otherwise roll back. Consider a transactional helper.                                       |
| **7  No checked exception in signature**                              | Method declares none; callers may assume rename can’t fail except for programming errors.                                                                    | Renaming touches formulas, shared strings, etc.—a genuine runtime failure (I/O, parse) is possible.                                                                    | Declare a single POI-specific **checked** `SheetRenameException` (extends `Exception`) so callers must handle failures in batch operations.              |

### c.
| Criterion       | Assessment of the current line                                                                                             | Why it is **unacceptable**                                                                                                                             | Recommended change                                                                                                                                        |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Fail-fast / no hidden data loss**  | The method truncates the user-supplied name without warning.                                                               | • Violates *principle of least astonishment*—callers think the full name was saved.<br>• Creates silent data corruption and makes debugging difficult. | **Reject rather than mangle.**<br>`throw new SheetNameTooLongException("Sheet names are limited to 31 characters (" + sheetname.length() + " supplied)")` |
| **Consistency & round-trip safety**  | After truncation, `getSheetName()` returns a string different from the one passed in.                                      | Breaks invariants that callers might rely on (e.g., renaming and then immediately reading the name back).                                              | Provide an overload or boolean flag such as `setSheetName(int, String, boolean allowTruncate)` so the caller consciously opts in.                         |
| **Explicit error-handling contract** | No indication in Javadoc that truncation occurs.                                                                           | API users must study the source to discover this behaviour; violates *“self-documenting code”* rule.                                                   | Document the length limit and the chosen behaviour **clearly in Javadoc**, or (better) expose a constant `MAX_SHEET_NAME = 31` and ask callers to check.  |
| **Atomicity of operation**           | Truncation happens before duplicate-name check, so collisions may still occur after truncation—subtle and order-dependent. | Edge-case bugs: two different 40-char names may collide after both are truncated.                                                                      | First **validate** length; if > 31, throw.  Only proceed with duplicate check once the candidate string is confirmed valid.                               |
